# LocalShare 局域网文件分享工具 —— 设计文档

- 日期：2026-08-27
- 状态：已确认（用户逐节审阅通过）
- 范围：MVP（需求分析 + 架构 + 协议规格 + 技术栈）

---

## 1. 概述

### 1.1 问题陈述

同一局域网内的多台异构桌面系统（Windows / macOS）之间，缺少一种"快速、直接、无需公网中转"的文件与文件夹互传方式。现有手段（U 盘、网盘、IM 软件、公网传输服务）要么依赖外设或外网，要么存在隐私与速度问题。

本工具的目标：**同一局域网内，不同系统之间快速、可靠地互相传递文件和文件夹，保持目录结构，交互直观。**

### 1.2 目标（MVP）

- Windows 与 macOS 双平台原生桌面应用，同一应用对等互传。
- 局域网内自动发现在线设备，也支持手动输入 IP 直连兜底。
- 文件与文件夹拖拽发送；文件夹逐文件流式传输，保持目录结构（含空目录）。
- 接收方确认机制：显示发送者、内容、大小，接受后才传输。
- 接收时若发生同名冲突，用户可选择"覆盖"或"存入其他文件夹"。
- 全程局域网直连，不依赖公网、无需账号。

### 1.3 非目标（MVP 明确不做）

- 断点续传（未来按需增加）
- 文本 / 剪贴板 / 消息传输
- 端到端加密、完整性哈希校验
- 传输历史持久化（仅会话内展示）
- 目录"镜像删除"（覆盖时不删除旧目录里本次未涉及的文件）
- 组播 / 跨 VLAN 发现、移动端、多传输并发、限速

## 3. 架构总览

单进程 Electron 应用。渲染进程负责 UI，主进程承载全部网络逻辑，二者通过 IPC（`contextBridge` + `ipcMain`/`ipcRenderer`）通信。

```
┌──────────────────────────────────────────────┐
│               Electron 应用（单进程）            │
│                                                │
│  ┌──────────────────────────────────────┐     │
│  │ 渲染进程 (Renderer)                   │     │
│  │  · 设备列表 / 传输列表 / 进度条 UI      │     │
│  │  · 拖拽上传区 / 确认对话框             │     │
│  └───────────────▲──────────────────────┘     │
│                  │ IPC (contextBridge)         │
│  ┌───────────────┴──────────────────────┐     │
│  │ 主进程 (Main)                         │     │
│  │  ┌────────────┐  ┌───────────────┐   │     │
│  │  │ Discovery  │  │ Transfer      │   │     │
│  │  │ (UDP 广播) │  │ (TCP 文件流)   │   │     │
│  │  └────────────┘  └───────────────┘   │     │
│  │  ┌────────────┐  ┌───────────────┐   │     │
│  │  │ Protocol   │  │ Storage       │   │     │
│  │  │ (帧/编解码) │  │ (保存/冲突)   │   │     │
│  │  └────────────┘  └───────────────┘   │     │
│  └──────────────────────────────────────┘     │
└──────────────────────────────────────────────┘
```

### 3.1 模块职责（单一职责、可独立测试）

- **Discovery（发现）**：UDP 广播自身存在、监听同类广播、维护在线设备表（心跳超时剔除）。仅用 Node 内置 `dgram`。
- **Protocol（协议）**：控制帧编解码、消息类型定义、路径清洗。纯函数、无网络 I/O，可完全单元测试。
- **Transfer（传输）**：TCP 连接管理、发起/接受传输、目录树遍历、逐文件流式收发、确认流程、进度汇报、状态机。
- **Storage（存储）**：保存目录管理、冲突检测、覆盖/换目录处理、`.part` 原子写、失败清理。
- **IPC（桥）**：preload 暴露的窄 API 白名单，渲染进程只能调用这些方法。

### 3.2 依赖方向

单向依赖：UI → IPC → 主进程服务。Discovery / Transfer 之间只通过 Protocol 定义的消息交互，互不直接依赖。

## 4. 服务发现协议（自研，UDP）

### 4.1 通道选择

- **UDP 子网广播**，不用组播。同一子网内必达，Windows / macOS 原生支持，实现最简。
- 广播受限场景（跨 VLAN、AP 隔离）由"手动输入 IP 直连"兜底。
- **手动直连端口约定**：输入 `IP` 时连接对方配置的传输端口（默认 `45556`）；输入 `IP:端口` 可指定非默认端口。

### 4.2 端口与启动策略

- 发现端口：`45555/UDP`（可配置）；传输监听端口：`45556/TCP`（可配置）。
- **严格使用配置端口，启动时若被占用，报错退出**，错误信息指明端口号。不做自动 +1。
- 两端均不需要管理员权限。

### 4.3 消息类型

| 消息 | 方向 | 内容 |
|------|------|------|
| `HELLO` | 周期性广播 | 设备ID、设备名、平台、版本、TCP监听端口、时间戳 |
| `BYE` | 下线时广播（尽力而为） | 设备ID |

- 发现是单向的：广播不要求应答，无响应机制。

### 4.4 心跳与设备表

- 每 3 秒广播一次 `HELLO`。
- 收到 `HELLO` 刷新设备表中对应设备的最后活跃时间；设备名以最新为准。
- 连续 12 秒（4 个心跳周期）未收到某设备 `HELLO`，标记离线并从列表移除。

### 4.5 设备 ID

- 首次运行生成 UUID 并持久化（electron-store，存于 `app.getPath('userData')`）。
- 重启后仍是同一台设备，设备表不会因重名/重启产生幽灵条目。

### 4.6 帧格式（发现消息）

发现消息与 TCP 传输控制帧（5.2）**同构**（magic + length + JSON），区别仅在载荷上限：

```
┌──────────┬──────────┬──────────────┐
│ 4B magic │ 4B length│ JSON payload │
│ "LS1\0"  │ uint32 BE│   ≤ 1 KiB    │
└──────────┴──────────┴──────────────┘
```

- magic 头过滤无关 UDP 流量；length 防粘包/拆包。
- 发现消息（UDP）载荷上限 1 KiB（UDP 报文小，HELLO/BYE 内容极少）；传输控制帧（TCP）上限 16 MiB（见 5.2）。

### 4.7 跨平台注意

- **macOS**：首次监听网络触发"本地网络"权限弹窗；应用内给出引导文案。
- **Windows**：首次运行防火墙弹窗，需允许"专用网络"；文档说明。
- 发现消息明文、无加密（局域网可信前提已接受，见需求基线 #5）。

## 5. 传输协议与数据帧（自研，TCP）

### 5.1 连接模型

- 每次传输 = 一条独立 TCP 连接（发送方主动连接接收方的传输监听端口）。
- MVP 单队列：同一时间只跑一个传输，其余在 UI 排队。
- 连接建立后第一帧必须是 `OFFER` 且 magic 匹配，否则立即断开（防误连）。

### 5.2 通用控制帧（TCP 控制消息共用）

```
偏移   长度   字段                说明
0      4      magic              ASCII "LS1\0" = 4C 53 31 00
4      4      length             uint32 大端序，JSON 载荷字节数（不含头）
8      N      payload            UTF-8 JSON，长度 = length
```

- 帧头固定 8 字节。
- `length` 上限 **16 MiB**（防御性限制；OFFER 清单按每文件约 60 字节估算可容纳约 25 万文件，超出则发送方拒绝并提示"文件数量过多，请分批发送"）。

### 5.3 消息类型与 JSON 载荷

**OFFER（发送方 → 接收方，连接后首帧）**

```json
{
  "type": "OFFER",
  "transferId": "uuid",
  "senderId": "device-uuid",
  "senderName": "Gary's MacBook",
  "fileCount": 3,
  "totalBytes": 120140,
  "files": [
    { "type": "file", "path": "docs/a.txt",       "size": 100 },
    { "type": "file", "path": "docs/img/b.png",   "size": 20000 },
    { "type": "dir",  "path": "docs/empty/" }
  ]
}
```

- `files` 顺序 = 发送顺序。
- `type: "file"`：走 FILE_HEADER → 裸数据 → FILE_DONE 流程。
- `type: "dir"`：仅建空目录（`mkdir -p`），不产生文件传输消息。
- `path` 统一 `/` 分隔的相对路径；接收方重建目录结构前必须做路径清洗（见 5.6）。
- 单文件传输 = 清单只有一个 `type: "file"` 条目，统一路径。

**ACCEPT / REJECT（接收方 → 发送方）**

```json
{ "type": "ACCEPT", "transferId": "uuid" }
{ "type": "REJECT", "transferId": "uuid", "reason": "user_declined" }
```

**FILE_HEADER（发送方 → 接收方，每个文件开始前）**

```json
{ "type": "FILE_HEADER", "transferId": "uuid", "path": "docs/a.txt", "size": 100 }
```

**FILE_DONE（发送方 → 接收方，每个文件流结束后）**

```json
{ "type": "FILE_DONE", "transferId": "uuid", "path": "docs/a.txt", "bytesWritten": 100 }
```

- `bytesWritten` 必须等于 FILE_HEADER 的 `size`，不等则视为协议错误、断开连接（检测发送端传输中途文件被改动）。

**TRANSFER_DONE / TRANSFER_ACK（发送方 ↔ 接收方）**

```json
{ "type": "TRANSFER_DONE", "transferId": "uuid" }   // 发送方：全部文件已发出
{ "type": "TRANSFER_ACK",  "transferId": "uuid" }   // 接收方：全部落盘确认
```

**CANCEL（任意一方，主动取消）**

```json
{ "type": "CANCEL", "transferId": "uuid", "reason": "user_cancelled" }
```

**取消语义（基于 TCP FIN）**：取消方停止数据流后发 `CANCEL`（尽力，对端若在 CTRL 模式可识别）并 `socket.end()`（FIN）。对端可靠感知：收到 FIN（`end` 事件）且传输未完成 → 判定「对方已取消」；收到 RST / 30 秒无数据超时 → 判定「连接断开」。传输中取消时 `CANCEL` 帧可能被接收方 DATA 模式吞掉，由 FIN 兜底——FIN 双向握手本身就是取消确认，无需应用层 ACK。

**ERROR（任意一方，致命错误）**

```json
{ "type": "ERROR", "transferId": "uuid", "code": "disk_full", "message": "接收方磁盘空间不足" }
```

### 5.4 数据流字节布局与读取状态机

一条 TCP 连接上，控制帧与裸文件字节流交替出现，靠 FILE_HEADER 声明的 `size` 精确切割：

```
[OFFER][ACCEPT]
[FILE_HEADER(f1)][ f1 的 size 字节裸数据 ][FILE_DONE(f1)]
[FILE_HEADER(f2)][ f2 的 size 字节裸数据 ][FILE_DONE(f2)]
...
[TRANSFER_DONE][TRANSFER_ACK]
```

接收方读循环为两态状态机：

```
┌────────────┐  FILE_HEADER 且 size>0   ┌────────────┐
│  CTRL 模式  │ ──────────────────────▶ │  DATA 模式  │
│ 读8字节头    │                          │ 精确读 size │
│ +JSON解析   │ ◀────────────────────── │ 字节写.part │
└────────────┘  读满 size，回 CTRL       └────────────┘
```

- **CTRL 模式**：读 8 字节头 → 读 `length` 字节 JSON → 解析分发；遇到 `FILE_HEADER`（size>0）切到 DATA 模式。
- **DATA 模式**：从流中精确读 `size` 字节写入 `.part`（边读边写，内存占用恒定），读满回 CTRL 模式。
- 粘包/拆包：控制帧靠 4 字节 length 头定界，裸数据靠 `size` 定界，无额外哨兵字节。

### 5.5 边界与编码约定

- 所有整数长度字段：**大端序（网络字节序）**。
- JSON：**UTF-8、无 BOM**。
- 文件大小 `size`：JSON 数字（IEEE754 双精度，精确整数上限 2^53 ≈ 9 PB，实际场景不会触及）。
- 零字节文件：`size=0`，FILE_HEADER 后不跟随裸数据，直接发 FILE_DONE。
- 裸数据不经过 JSON、不加封装，直接是文件字节。

### 5.6 路径安全

接收方对清单中每个 `path` 做清洗后再落盘：

- 拒绝 `..`（路径穿越）、绝对路径（`/` 开头、盘符开头如 `C:\`、`~`）。
- 拒绝非法字符（Windows 保留字符 `\ / : * ? " < > |` 及控制字符、保留名 `CON`、`NUL` 等）。
- 清洗后仍异常的路径：作为协议错误处理——断开连接并报错，不静默跳过。

### 5.7 完整时序（发送方视角）

```
发送方                                  接收方
  │  TCP connect                         │
  │ ── OFFER(传输ID/设备名/清单) ───────▶│  检测冲突 → 弹确认框
  │ ◀── ACCEPT ───────────────────────── │  （或 REJECT → 关闭）
  │ ── FILE_HEADER(相对路径, 大小) ─────▶│
  │ ── 裸字节流 ────────────────────────▶│  写入 file.part
  │ ── FILE_DONE ──────────────────────▶│  改名 file（原子落盘）
  │        （重复：清单里的每个文件）      │
  │ ── TRANSFER_DONE ──────────────────▶│
  │ ◀── TRANSFER_ACK ─────────────────── │  确认全部落盘
  │  关闭连接                            │
```

### 5.8 超时与失败

- OFFER 发出后 **3 分钟**无 ACCEPT/REJECT → 发送方取消并提示"对方无响应"。
- TRANSFER_DONE 发出后 **30 秒**无 TRANSFER_ACK → 发送方判定失败。
- 传输中（接受后/传输阶段）**30 秒**无数据流动 → 双方判定连接死：接收方清理 `.part`。
- 任意时刻连接中断 → 双方标记失败，接收方清理该传输的 `.part`。
- 文件在传输中被修改：清单记录遍历时的大小，实际以流为准；不做一致性校验（MVP 明确不做哈希校验；若 FILE_DONE 的 bytesWritten 与 size 不符则按协议错误断开）。

## 6. UI/UX 设计

### 6.1 界面结构（单窗口）

```
┌─────────────────────────────────────────────┐
│  LocalShare                    [设置 ⚙]      │
├───────────────┬─────────────────────────────┤
│ 在线设备       │                             │
│ ┌───────────┐ │    ┌───────────────────┐    │
│ │ 🖥 Gary-Mac│ │    │                   │    │
│ │ 🖥 Win-PC  │ │    │  拖拽文件/文件夹    │    │
│ │           │ │    │  到此处发送         │    │
│ └───────────┘ │    └───────────────────┘    │
│               │                             │
│ (手动输入IP)   │  传输队列                    │
│               │  ▸ 发送 video.mp4  68% ▓▓▓░  │
│               │  ✓ 已完成 a.txt              │
├───────────────┴─────────────────────────────┤
│  设备名: Gary-Mac · 保存到: ~/LocalShare      │
└─────────────────────────────────────────────┘
```

- **左侧设备列表**：在线设备（设备名 + 平台图标），底部"手动输入 IP 直连"入口。
- **中间拖放区**：拖入文件/文件夹发起发送；多台在线设备时弹出设备选择，单台直接发。
- **下方传输队列**：进行中（当前文件 + 总体进度条）、已完成、已失败、已拒绝；按会话保留，不持久化。
- **设置页**：设备名、保存目录、UDP/TCP 端口（修改端口后重启生效）。

### 6.2 交互流

- **发送**：拖入文件 → 选定目标设备 → 建立连接并发 OFFER → 等对方确认 → 传文件 → 收 TRANSFER_ACK → 显示"已完成"。
- **接收**：收到 OFFER → 系统确认框（发送者设备名、内容、文件数、总大小、保存位置、"接受 / 拒绝"）→ 接受则收（显示进度），拒绝则回 REJECT，双方显示"已拒绝"。

### 6.3 冲突处理（接收时用户决策）

冲突检测时机：接收方收到 OFFER 后、弹确认框之前，检查清单路径与保存目录是否冲突（存在同名文件或同名目录）。

确认框（仅检测到冲突时显示冲突选项）：

```
┌────────────────────────────────────────────┐
│  接收传输？                                  │
│  发送者: Gary's MacBook                     │
│  内容:  work/  (12 个文件, 48.3 MB)         │
│  保存到: ~/LocalShare/work/                 │
│  ⚠ 保存位置已存在同名文件/文件夹              │
│                                            │
│  [ 接受并覆盖 ]  [ 选择其他位置 ]  [ 拒绝 ]   │
└────────────────────────────────────────────┘
```

- **接受并覆盖**：本次传输中所有同名文件直接覆盖目标位置；空目录冲突按 `mkdir -p` 合并语义。覆盖仍走 `.part` → rename 原子写路径。
- **选择其他位置**：用户为本次传输指定新的目标目录（仅本次生效，不改默认保存目录）；新位置仍有冲突则再次呈现选择。
- **拒绝**：回 REJECT，结束。
- **无冲突时**：确认框仅"接受 / 拒绝"。
- **不做自动重命名**（移除 `file (1).txt` 方案）。
- **覆盖语义边界**：逐文件覆盖，不先删除旧目录——旧目录中本次未涉及的文件保留（"镜像删除"不在 MVP，见 1.3）。

## 7. 错误处理清单

| 场景 | 行为 |
|------|------|
| 端口被占 | 启动报错退出，指明是哪个端口 |
| 发起时设备已离线 | UI 提示"设备不在线"，不建立连接 |
| OFFER 60 秒无响应 | 发送方取消，提示"对方无响应" |
| 接收方拒绝 | 正常结束，双方显示"已拒绝" |
| 传输中断（连接断开/崩溃） | 双方标记失败，接收方清理 `.part` |
| 磁盘满 / 无写权限 | 接收方发 `ERROR(code)`，发送方显示原因 |
| 文件名冲突 | 接收时用户选择：覆盖 / 其他位置 / 拒绝 |
| 路径穿越 / 非法文件名 | 接收方清洗路径，异常即断开并报协议错误 |
| macOS 本地网络权限 | 应用内引导文案 |
| Windows 防火墙 | 文档说明需允许"专用网络" |

## 8. 技术栈

### 8.1 技术选型

- **桌面框架**：Electron
- **前端**：Vue 3 + TypeScript + Vite
- **状态管理**：Pinia（设备列表、传输队列等 UI 状态）
- **UI 组件库**：Element Plus（拖拽上传、进度条、对话框、消息提示）
- **网络层**：Node 内置 `dgram`（UDP 发现）+ `net`（TCP 传输），**从零自研，零第三方网络依赖**
- **持久化**：electron-store（设备 ID、设置项）
- **工程脚手架**：electron-vite（统一构建主进程/预加载/渲染进程）+ electron-builder（打包 `.dmg` / `.exe`）
- **测试**：Vitest（单元 + 集成，node 环境跑回环地址）

### 8.2 边界说明（防混淆）

"从零自研、零第三方依赖"的约束**仅作用于网络层**（发现协议 + 传输协议 + 帧编解码）。UI 框架、组件库、构建打包、持久化、测试工具链均采用业界成熟方案。

### 8.3 决策记录（WHY）

| 决策 | 理由 |
|------|------|
| Electron 覆盖项目默认"语言纯净性约束" | 用户在本设计中**知情明确选择**（约束被提前告知后仍选 Electron），本轮用户请求优先于项目规范默认值 |
| 单进程架构 | MVP 复杂度最低，状态集中于一处；进程隔离的价值在 UI 崩溃频繁时才体现，现阶段是过度设计 |
| UDP 广播而非组播 | 同子网必达、双平台原生支持、实现最简；跨 VLAN 由手动直连兜底 |
| 端口严格配置、被占报错退出 | 用户明确要求，行为可预期；HELLO 携带实际 TCP 端口，配置漂移无必要 |
| 接收方确认（非加密） | 用户明确选择；局域网可信前提，快速分享优先 |
| 逐文件流式（非打包） | 立即开始、文件粒度进度、无临时磁盘占用 |
| 冲突"覆盖/换位置"而非自动重命名 | 用户明确要求（多次同步同一目录是典型场景），避免产生难以清理的副本 |
| 网络层自研 + UI 层成熟方案的分层 | 用户两条要求的分层整合：网络协议可控可审计，UI 工程化效率优先 |
| 国内镜像固化进仓库 | 用户在中国，npm 包与 Electron 二进制直连下载慢；`.npmrc` 提交进仓库保证开箱即用 |

### 8.4 国内镜像与安装配置

仓库内固化 `.npmrc`（提交进仓库）：

```ini
registry=https://registry.npmmirror.com
electron_mirror=https://npmmirror.com/mirrors/electron/
electron_builder_binaries_mirror=https://npmmirror.com/mirrors/electron-builder-binaries/
```

- 首次安装：`npm install`，`.npmrc` 已接管 registry 与 mirror，无需额外传参。
- 打包：electron-builder 自动读取 `electron_builder_binaries_mirror`，winCodeSign / nsis 等不再从 GitHub 拉取。
- 个别包若镜像未同步：`npm install <pkg> --registry=https://registry.npmmirror.com` 或临时回退官方源。
- 代码托管可选用 Gitee / GitCode 作为 GitHub 的国内加速通道（仅建议）。

## 9. 测试策略

### 9.1 单元测试（Vitest，纯逻辑无网络）

- Protocol：帧编解码、粘包/拆包、零字节文件、超长载荷、magic 校验、非法 JSON、`bytesWritten` 不符检测。
- 路径清洗：`..`、绝对路径、非法字符、Windows 保留名、空路径的拒绝用例。
- Storage：冲突检测、覆盖语义、`.part` 原子写、失败清理。
- 目录树遍历：嵌套目录、空目录、符号链接处理（**跳过符号链接**，防循环）。

### 9.2 集成测试（Vitest node 环境，真实网络回环地址）

- 两个 Transfer 实例（一个监听、一个连接）跑完整流程：OFFER → ACCEPT → 逐文件 → TRANSFER_DONE → TRANSFER_ACK。
- 场景：单文件、多文件 + 目录结构、空目录、冲突覆盖、拒绝、连接中断、错误帧。
- 在 `127.0.0.1` 上执行，CI 可跑，不依赖真机。

### 9.3 组件测试（可选）

- 确认框、传输列表的核心交互（Vue Test Utils），视成本决定是否纳入 MVP。

### 9.4 跨平台冒烟（手动，发布前）

- Windows + macOS 各一台：自动发现互通、防火墙 / 本地网络权限弹窗、拖拽 UX、1GB 大文件传输。

### 9.5 成功标准

- Win/Mac 同局域网可互相发现，设备列表 12 秒内出现/消失。
- 拖拽文件/文件夹 → 确认 → 传输完成，目录结构完整（含空目录）。
- 冲突场景"覆盖 / 换位置"可用；拒绝、中断、离线均有清晰提示。
- 千兆局域网 1GB 文件传输可用，CPU 占用合理。
