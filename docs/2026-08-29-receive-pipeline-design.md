## 1. 背景与动机

### 1.1 现状问题

接收方当前"边收边写"：每个 socket 数据块直接写入 `.part` WriteStream（1MB 缓冲），
磁盘写入缓冲一满立即 `socket.pause()`。磁盘的**瞬时状态**直接映射为**网络停顿**：

```
磁盘毫秒级停顿（flush / Defender 扫描 / 系统写入高峰）
→ WriteStream 缓冲满 → socket.pause() → TCP 零窗口
→ 发送方减速 → 拥塞窗口收缩 → 恢复需重爬
```

实测佐证（probe-gap.mts，回环）：协议层本身无空泡（文件边界间隙中位 0ms、
连续流 815 MB/s），慢的根源在背压直连的灵敏度，而非协议结构。

### 1.2 讨论中否决的备选方案（记录理由）

| 方案 | 否决理由 |
|------|----------|
| 逐文件确认后发下一文件 | 单连接下每文件插入 RTT 空泡，比现状连续推进更慢；流水线收益由队列解耦自动获得 |
| 无上限内存缓冲 | 积压速率 × 时长可推向数十 GB → OOM 崩溃 → 重传全部；512MB 有界是收益/风险平衡点 |
| 应用层固定分块协议 | TCP 零窗口流控 + 水位背压已覆盖其全部功能且粒度更细 |

### 1.3 用户拍板的边界决策

- **崩溃/断电丢失内存队列数据：接受**，重传解决，不做落盘前持久化保证
- 发送方"已发送"与接收方"已接收"分阶段显示是**设计内行为**
- 磁盘持续慢于网络时总时长受磁盘物理上限封顶，方案目标是"网络通路不被磁盘拖累"，
  不是突破磁盘极限

## 2. 核心架构：收包与落盘解耦

```
网络线程（主进程事件循环）                写盘循环（异步顺序消费）
──────────────────────────────      ─────────────────────────────────
socket.on('data')                     while (队列非空) {
  → CTRL/DATA 状态机解析                 取队头数据 → 写 .part
  → 文件数据入内存队列（不碰磁盘）          FILE_DONE → flush + rename
  → 文件 N 全部入队                       → 发 FILE_ACK(N)（可选帧，见 §4）
  → 水位监测（见 §3）                     全部落盘完成 → 回 TRANSFER_ACK
                                       }
```

设计要点：

- **单队列单写盘循环**：FIFO 保序；FILE_DONE 的 rename 在该文件全部字节出队后
  执行，逐文件原子落盘语义不变。不做每文件独立写线程（乱序 commit、HDD 随机寻道、
  崩溃清理状态机复杂化，均为负收益）
- **"线程"是逻辑概念**：Node 单进程事件循环内的异步写循环，不引入
  worker_threads（跨线程数据拷贝反而更慢）
- **网络线程不碰磁盘**：入队纯内存操作；`mkdirSync` 等同步调用移出接收路径
  （§6 P1'）

## 3. 水位背压（滞回控制）

```
入队后检查：queuedBytes > HIGH_WATER (384MB) → socket.pause()
写盘循环：消费至 queuedBytes < LOW_WATER (128MB) → socket.resume()
```

- **高/低水位滞回区间**：避免在阈值附近高频 pause/resume 抖动
- **内存上限**：512MB（高水位 384MB + 写缓冲余量），硬顶即 ACCEPT 前可配置
- **pause/resume 机制完全复用现有实现**（TCP 零窗口流控，发送方内核自动停发，
  连接保持、ACK 照发只是窗口归零——与"没收到 ACK"的故障路径有本质区别，
  有窗口探测保活，连接不会被误判死亡）
- 磁盘持续慢于网络时：队列稳定在高位、背压持续生效，链路速度 = 磁盘速度
  （物理极限），但传输**稳定完成**而非 OOM 失败

## 4. 分阶段确认（FILE_ACK）

### 4.1 新增帧

```json
{ "type": "FILE_ACK", "transferId": "uuid", "path": "docs/a.txt" }
```

接收方在**文件 N 的全部数据字节入队**后立即发送（不等落盘）。

### 4.2 确认语义分级

| 帧 | 触发时机 | 发送方显示 | 接收方显示 |
|----|----------|-----------|-----------|
| FILE_ACK(N) | 文件 N 数据全部入内存队列 | 该文件"已送达"（可显示） | — |
| TRANSFER_ACK | 全部文件落盘完成 | 传输"已完成" | 传输"已接收" |

- 发送方先完成、接收方稍后完成是**设计内行为**（用户已确认接受）
- FILE_ACK 是**可观测性增强**，不改变传输推进逻辑（单连接下逐文件等待确认
  反而插入 RTT 空泡，已否决——见 §1.2）
- **兼容性**：旧版本接收方不认识 FILE_ACK 会忽略（未知帧类型默认丢弃），
  发送方对 FILE_ACK 缺失有超时兜底（TRANSFER_ACK 仍为最终判据）

### 4.3 UI 状态分级

传输列表状态增加中间态：`已送达对端`（收到全部 FILE_ACK）→ `已完成`（TRANSFER_ACK）。
接收方不变（落盘完成才显示）。

## 5. ACK 超时动态化

现状 `ACK_TIMEOUT_MS = 30s` 固定值，在"发完但队列尚有积压"场景会误杀
实际会成功的传输（512MB @ USB 2.0 磁盘排空需 ~15s+，慢盘更长）。

**方案**：发送方等 TRANSFER_ACK 的超时改为

```
timeout = 30s + totalBytes / DISK_DRAIN_RATE (保守值 20 MB/s)
```

例：1GB 传输 → 30s + 51s ≈ 81s 窗口。动态值只放宽不收紧，防御性设计；
无需接收方心跳帧（初始实现从简，若实测仍误杀再加）。

## 6. 配套正确性修复（先行独立提交）

| # | 问题 | 修复 |
|---|------|------|
| P1 | `FILE_DONE.bytesWritten` 报遍历清单值而非实际发送值 → 接收方校验形同虚设，文件传输中被截断会导致后续帧被误当数据、**数据错位落盘** | `pipeFile` 统计实际字节，FILE_DONE 报实际值；补"传输中截断文件"集成测试 |
| P2 | `pipeFile` 每文件挂 `drain`/`error` 监听器且从不摘除 → 监听器累积泄漏（实测 MaxListenersExceededWarning） | 完成时 `removeListener` / `once` + 显式清理 |
| P3 | walkPaths 静默跳过符号链接，用户无感知 | 返回跳过计数，发起时 UI 提示"已跳过 N 个符号链接" |
| P1' | `AtomicSink.open` 每文件 `mkdirSync`（同步阻塞事件循环） | 目录存在性缓存去重（Map），仅首次创建 |

## 7. 实施顺序与验证

```
1. P1/P2/P3/P1'  → 验证：全量测试 + 新增截断/泄漏回归用例
2. 方案 2 主体    → 验证：慢磁盘模拟集成测试（限速写）
3. FILE_ACK + 动态超时 → 验证：分阶段确认时序
4. UI 状态分级    → 验证：dev 模式双端人工核对
5. probe-gap 复测 → 对比：慢盘场景块间隙/pause 次数/总时长
```

### 成功标准

- 慢磁盘（模拟 10MB/s）+ 100MB 文件：传输完成不误判超时；pause 次数
  相比现状大幅下降（目标：抖动场景 0 次被动 pause）
- 快磁盘 + 多文件：总时长不低于现状（回归保护）
- 磁盘抖动模拟（间歇性延迟）下，网络侧数据流无空档（probe-gap 验证）
- 内存占用：任何场景 ≤ 512MB + 常数
- 全量测试通过（53+ 用例，新增慢盘/截断用例）

## 8. 预期收益总结

| 场景 | 现状 | 优化后 |
|------|------|--------|
| SSD 抖动（快盘+间歇停顿） | 锯齿降速（可达 30%） | 匀速满带宽，抖动被队列吸收 |
| 海量小文件 | commit 期间网络空转 | 收 N+1 与写 N 重叠，数倍提升 |
| 大文件+慢盘 | 稳定 = 磁盘速率 | 总时长不变（物理极限），但链路稳定、无误杀、发送方提前释放 |
| 大文件+快盘 | 背压直连偶尔触顶 | 全程网络速率 |

**一句话**：磁盘瞬时状态不再映射为网络停顿，映射改为宏观积压量——在磁盘
"够快但抖"的绝大多数真实场景里，网络通路跑到满速。
