## 0. 这份抓包是什么（先钉死分析对象）

**是。这份抓包就是当时那次大文件传输的现场抓包，且抓包期间传输全程在进行中。**
不是回环测试、不是合成流量、不是事后构造。五条可核对的事实：

| 事实 | 数值 | 说明 |
|---|---|---|
| 是 LocalShare 的数据通道 | 端口 **45556**，`10.16.1.24` → `10.16.1.213` | 45556 = 本应用 TCP 端口；两端是两个真实主机 |
| 抓到了实打实的文件数据 | 单向 **181.83 MB / 125,594 段**，26.644 s | 平均 1448 B/段，MTU 1500 的正常文件流 |
| 是「大文件」而非小文件集合 | 26.6 s 内正向流中 `LS1\0` 帧头出现 **0 次** | 没有任何 `FILE_HEADER/FILE_DONE`，即全程都是**同一个文件**的数据 |
| 文件确实很大 | 接收端自报累计已收 **175.79 MB → 356.69 MB** | 抓包只是这个 ≥356.7 MB 单文件传输的**中段**；`transferId` 唯一：`f1e95652-...` |
| 抓到的就是「慢」的那一段 | **6.825 MB/s = 54.6 Mbit/s** | 这就是用户体感慢的实测速率；抓包期内速率无中断（1 s 窗口 4.71~10.04 MB/s） |

补充两点排除性证据：

- **不是回环/合成**：同一台主机（10.16.1.24）在抓包期内还有 **30 条无关 TCP 会话**
  （外部 HTTPS、视频等），且报文是真实以太网帧（MSS 1448、TCP 时间戳）——真实主机上的一次真实使用。
- **传输确实一直在推进**：接收端 266 个 `RECV_PROGRESS` 帧的累计计数从 175.79 MB 单调推进到
  356.69 MB（每 100 ms 增量中位 762 KB）。看起来的「回退」只有个别样本，经查是**反向控制帧被 TCP
  重传、携带旧计数**（同一 seq 出现 6 次 = 被重传 5 次）——顺带证明**反向链路也在丢包**。

> 关于分析精度的两点保留（不影响上面的判定，只影响个别细节的精度）：
> ① 抓包点在网卡驱动之上，同一批次的µs级时间戳被压平，故本报告只用聚合量与 >1 ms 间隔；
> ② 未抓到 TCP 握手，窗口扩大因子 ws 未知，故用下界推断（§3.3 给出两条独立证据）。

## 1. 核心原因（一句话）

> **整个传输从头到尾只用了 1 条 TCP 连接；这条连接的拥塞窗口被路径上 0.358% 的丢包压在 ~136 KB，
> 在 18~20 ms 的环路反馈时延下，吞吐被锁死在「窗口 ÷ 时延」= 136 KB ÷ 20 ms ≈ 6.8 MB/s。
> 链路有 98.3% 的时间处于空闲。**

因果链（每一环都有 §3 的实测数字支撑）：

```
链路队列溢出——丢包成串（41 串，中位 4 段，最长连续 62 段 ≈ 90 KB）
  → TCP 快速重传 + cwnd 减半（CUBIC）→ cwnd 长期停在 100~400 KB 带（中位 136 KB）
  → 每个 RTT 只能推进一个窗口；接收端按 GRO 每 ~43 KB 才回一个 ACK，
    把有效环路时延从物理下界 5.15 ms 拉到 18~20 ms
  → 吞吐 = cwnd ÷ 环路时延 ≈ 6.8 MB/s  ← 实测 6.825 MB/s
```

**已被实测排除的（不是原因）**：接收端落盘/背压、接收窗口、协议结构、发送端读盘能力 —— 逐条见 §4。
**发送端应用层的「1 MB 一停一等」只是次要放大器**：它造成的空洞占**总时长 17.7%（4.72 s）**，修掉上限 **+22%**；
而 §3.7 的决定性判据显示 —— **窗口一开，91.4% 的情况下发送端 2 毫秒内就能把窗口填满**，全程释放多少窗口就补上多少。
所以定速的是**窗口开得多快**，不是供数快不快；供数不足只出现在每个 1 MB 循环的尾端。

**唯一还没测的不是「为什么慢」，而是「还能快到多少」**：链路的物理上限。
它只决定并行连接能把 6.8 MB/s 提到 3 倍还是 10 倍，**不改变上面的根因判定**（§4 假设 F、§5 P0）。

> 与既有设计文档的关系见 §7：`docs/receive-pipeline-design-2026-08-29.md` §1.1 把根因归为
> 「磁盘抖动 → 背压 → 网络停顿」，本次抓包不支持该结论（该结论源自回环压测，回环不触发写背压，
> 因此复现不出真实链路的问题）。

### 1.1 一个必须澄清的常见误读

> **误读**：「慢是因为每发完 1 MB，就要等磁盘写入完成，然后再继续发。」

**不成立，三处错位：**

| 误读 | 实际情况 |
|---|---|
| 「等**磁盘写入**」 | 发送端**不写盘**，只**读**盘。发送端那份 1 MB 的停顿发生在 `sender.ts:81`：`socket.write(1MB)` 返回 false → `stream.pause()`，等的是 **`drain`（Node 写缓冲全部交给内核）**，这是**被网络排空速率驱动**的事件，不是磁盘事件。 |
| 「每 1 MB 一次」 | 抓包里的主导节奏是 **median 7.86 ms / 84 KB 一次突发**（共 1,894 次），与「1 MB 一循环」对不上：按实测 6.8 MB/s，一个 1 MB 的应用循环应为 **≈147 ms**，比观测到的主节奏大 **19 倍**。 |
| 「这是主因」 | 这种供数停顿只占**总时长 17.7%（4.72 s）**，修掉上限 **+22%**；更关键的是 §3.7 实测：窗口一开，**91.4% 的情况下 2 毫秒内就被填满**（累计释放 181.47 MB 就补上 184.96 MB）——发送端手上几乎一直有货，说明它不是在等本地磁盘。 |

**判据（为什么能确定 77% 不是本地等待）**：一次「本地无数据可发」的停顿结束时，
此前发出去的数据必然已被全部确认（在途 → 0）；而实测 76.9% 的停顿结束时**在途数据仍在**，
说明发送端手里有货、只是窗口不放行 —— 这是**网络/窗口受限**，不是本地磁盘受限。

**那接收端的磁盘写呢？** 接收端确实写盘，但它与网络已解耦（`receiver.ts:154-157` 内存队列 +
`receiver.ts:40-41` 高低水位），
且本次被抓包的证据排除了它：**零窗口通告 0 次**、接收窗口始终 ≥703 KB、接收端自报 ingest
6.796 MB/s 与发送端一致。若接收端磁盘慢于此，队列会持续堆积 → TCP 接收窗口必然收缩到 0
（这正是磁盘背压传导到网络的唯一途径）—— 本次 26.6 s 内一次都没有发生。
（严格说：这只证明**该接收端磁盘在该次传输中 ≥6.8 MB/s**，不证明它很快。）

**什么情况下「磁盘」才会真的成为主因**：接收端磁盘 < 网络速率时，队列会持续堆积直到 384 MB 高水位，
接收窗口随之收缩直至归零。**下次遇到疑似慢盘，判据是「抓包里有没有零窗口 ACK」**，
或看接收端队列峰值是否逼近高水位（§5 P5 已建议把该指标打日志）。

**同一份代码为何在不同机器上体感差别很大**：发送端这类空洞的长度 = 本地供给延迟。
快 SSD/页缓存上每 1 MB 只丢 0.2~1 ms（几乎无感）；**外置硬盘、加密卷、网络盘或磁盘繁忙时
每 1 MB 可能丢 30~50 ms**，占比就会远超 23%、甚至反超网络因素。判据同样简单：
看发送间隙结束时**在途字节是否 ≈0**（§5 P2）。

## 3. 关键测量结果

### 3.1 速率：稳定低速率，不是锯齿

1 s 窗口吞吐：mean **6.73**、median **6.50**、min 4.71、max 10.04、stdev 1.28 MB/s

```
[5.3, 5.1, 5.4, 4.7, 7.5, 6.2, 6.5, 8.7, 8.1, 7.7, 10.0, 8.4, 6.2, 6.8, 7.4, 7.0,
 7.9, 7.9, 6.0, 7.2, 5.7, 5.7, 6.1, 5.1, 6.2, 7.4, 5.6]   (MB/s)
```

速率**没有** 3~5 倍的锯齿（若 cwnd 被丢包反复砍半会出现）；它是一个被压在 4.7~10 MB/s 的
**稳定工作点**。100 ms 粒度最高 20.3 MB/s（162 Mbit/s），说明主机侧瞬时能递交更高，
但持续 1 s 从未超过 10.04 MB/s。

### 3.2 发送结构：ACK 时钟驱动（关键判据）

| 指标 | 值 |
|---|---|
| 突发数（>1 ms 间隔切分） | 1,894 |
| 每突发字节 | median **83,984**、mean 96,005、max 405,440 |
| 突发间隔（= 空闲） | median **7.86 ms**、mean 13.83 ms、p90 23.04 ms、max 131.55 ms |
| 空闲总时长 | 26.179 s / 26.644 s = **98.3%**（即抓包点看只有 1.7% 时间在递交） |
| **突发起点距上一个反向包** | median **0.105 ms**，**≤0.5 ms 的比例 = 95.1%** |
| >5 ms 空闲中「期间仍有反向包到达」 | **1,289 / 1,361 = 95%** |

**解读**：发送端 95% 的突发都在收到反向包后 0.1 ms 内发出 —— 这是标准的
**ACK 时钟（窗口）驱动**行为；而 95% 的空闲期间**仍在收到 ACK** 却不发数据，
说明窗口已经用满（收到的是不推进窗口的重复 ACK）。两条一起排除「发送端可以随便发但不发」
（即排除纯应用层饥饿）和「链路被持续灌满」（若是链路瓶颈，递交会连续铺开而非 0.1 ms 内一堆+长时间静默）。

### 3.3 窗口：接收窗口不是限制，拥塞窗口才是

| 指标 | 值 |
|---|---|
| 接收窗口（原始 16 位字段） | min 22,504 / median 29,221 / max 65,535 |
| **零窗口通告** | **0 次** |
| 达到 16 位上限 65,535 的比例 | 10.2% |
| 发送端在途字节 flight | p10 44,888 / **median 139,008** / p90 270,776 / max 664,632 |
| `flight / 原始窗口` 比值 | median 4.45、**max 22.75** |
| 最大突发 | 405,440 B（280 段无间隔连发） |

**两条独立证据链证明接收窗口远大于在途量**：

1. 在途量受 `min(cwnd, rwnd)` 约束，故 `flight/rwnd_raw ≤ 2^ws`；实测比值最大 **22.75** →
   窗口扩大因子 **ws ≥ 5**（×32），接收窗口实际 **≥ 703 KB**，而 flight 中位数仅 136 KB。
2. 发送端曾**一次连发 280 段 / 405 KB 而不等待** —— TCP 不可能越过窗口连发，
   故当时接收窗口 ≥ 405 KB。

结论：接收端既没有暂停读（`receiver.ts:257` 的 `socket.pause()` 不会发生，见 §1 第 2 点），
也没有窗口封顶。**瓶颈是 cwnd。**

### 3.4 丢包：真实、且成串

| 指标 | 值 |
|---|---|
| 抓包内序号空洞数 | **0**（抓包在发送点无丢包） |
| 重传段 | **450 段 / 0.651 MB = 0.358%** |
| 重传串数（序号空间连续） | 41 |
| 串长（段） | median **4**、mean 11.0、**max 62**（≈ 90 KB 连续丢失） |
| 串长分布 | 2 段 13 串、4 段 9 串、6 段 4 串、8 段 2 串、**≥10 段 13 串** |
| 丢包事件间隔 | median 0.000 s（同一窗口多个洞）、mean 0.565 s、max 7.342 s |
| 丢包恢复附加耗时 | 合计 0.79 s（3.0%），单次 median 15.6 ms |

**关键**：抓包点无空洞（序号覆盖完整）却有 450 段被重发 —— 说明这些段**确实被发出去过**，
是**链路上真的丢了**（若是抓包丢包，序号空间会出现空洞）。丢包**成串**（最多 62 段连续）是
**队列溢出/尾丢弃**特征，而非随机误码（随机误码是孤立单段）。

### 3.5 环路时延与 ACK 聚合

| 指标 | 值 |
|---|---|
| RTT（序号/确认号推算，含接收端 ACK 聚合延迟，是**上界**） | min **5.154** / median **18.03** / p90 72.55 / max 293.29 ms |
| 每个 ACK 确认字节 | median 34,752、mean 42,892 → **约 29.6 段/ACK** |
| ACK 到达间隔 | median 0.002 ms（成簇）、**mean 6.29 ms** |
| 推算环路速率 | 42,892 B / 6.29 ms ≈ **6.82 MB/s**（与实测吞吐 6.825 MB/s 吻合） |

接收端按 GRO 批次聚合 ACK（约 43 KB 一次），ACK 簇与数据突发一一对应。
**环路速率 = 每 ACK 释放的字节 ÷ ACK 间隔**，而每 ACK 释放的字节又被 cwnd 限制 —— 闭环自洽。

### 3.6 接收端真值（RECV_PROGRESS 帧）

| 指标 | 值 |
|---|---|
| 样本 | 266（每 100 ms 一帧，抓包期内无中断） |
| 起始已收 → 结束已收 | 175.79 MB → **356.69 MB**（单调推进；每 100 ms 增量中位 762 KB） |
| 接收端速率 | **6.796 MB/s**（发送端 6.825 MB/s，差 0.4%） |
| 含义 | 接收端 ingest 平滑跟随 —— **接收端不是瓶颈**，且磁盘持续写入能力 ≥ 7 MB/s |
| 反向链路状况 | 有 1 个控制帧被 TCP 重传 5 次（同一 seq 出现 6 份）→ **反向链路也在丢包** |

### 3.7 谁在定速：窗口还是发送端供数？（决定性判据）

**判据**：窗口每释放一块（确认报文推进了确认号），发送端能否立刻把它重新填满？
能填满 ⇔ 发送端手上有货 ⇔ 限速在窗口；填不满 ⇔ 供数跟不上。
（这个判据比「空闲结束时在途是否归零」更硬：前者直接测「有没有货」，后者只是间接推断。）

把推进确认号的确认报文按 0.5 ms 聚簇，比较「该簇释放的窗口」与「其后 2 ms 内实际发出的字节」：

| 指标 | 值 |
|---|---|
| 确认簇数 | 1,908 |
| 补货比（发出字节 ÷ 释放窗口） | p10 **1.00**、中位 **1.00**、p90 1.24 |
| 比值 ≈1（把窗口重新填满） | **1,743 簇（91.4%）** |
| 比值 0.5~0.9 | 89（4.7%） |
| 比值 0.1~0.5 | 53（2.8%） |
| 比值 <0.1（几乎没补，手上没货） | 9（0.5%） |
| 累计 | 释放 **181.47 MB**，2 ms 内补上 **184.96 MB**（比 1.02，超出部分是重传） |

**结论：91.4% 的情况下，窗口一开，发送端 2 毫秒内就把它填满；全程释放多少窗口，就补上多少。**
所以**定速的是窗口开得多快（确认时钟），不是发送端供数快不快**。这同时也是「介质没有被灌满」的
直接证据：若发送端始终有货而介质仍空闲，说明限制在窗口，而不在介质带宽。

**那 1 MB 循环的空洞算什么**：供数不足只出现在每个 1 MB 循环的尾端（见下），时间口径上约占 4.7 s。

**时间口径归因**（只统计 >25 ms、即远大于 18 ms 环路时延的间隙；此时若发送端真有货，
先前发出的数据必然已被确认，故「在途<8 KB」才是可信的「手上没货」证据）：

| 归因 | 判据 | 时长 | 次数 |
|---|---|---|---|
| **应用层供数不足** | 间隙 >25 ms 且结束时在途 < 8 KB | **4.72 s（占总时长 17.7%）** | 50 |
| **网络/窗口受限** | 其余 | ~21.5 s（82.3%） | — |

即：只修应用层供数，上限 **8.29 MB/s（+22%）**；若用更宽松的口径（>5 ms 间隙）则为 5.67 s / +27%。
两种口径都指向同一结论：**大头（约 82%）由窗口决定**，供数不足是次要项。

### 3.8 量纲校验（Mathis 方程）

`BW ≈ (MSS/RTT) × 1.22/√p`，取 MSS 1448 B、p = 0.358%、RTT ≈ 5.15 ms（实测下界）：
`(1448/0.00515) × 1.22/0.0598 ≈ 5.7 MB/s`，与实测 6.8 MB/s 同量级。
**这说明本传输正处在 TCP 的丢包受限稳态**，符合 §3.4 的真实丢包结论。

## 4. 根因判定（排除法）

| 假设 | 证据 | 判定 |
|---|---|---|
| A. 接收端磁盘慢 / 落盘背压传导为网络停顿 | 零窗口 0 次；接收窗口 ≥703 KB；接收端自报速率 6.796 MB/s 与发送端一致；384 MB 高水位数学上不可能触发（累计 356.7 MB） | **排除** |
| B. 发送端应用喂不上数据（读盘慢 / 事件循环卡） | **窗口一开，91.4% 的情况 2 ms 内即被填满**（累计释放 181.47 MB / 补上 184.96 MB）→ 供数绝大多数时刻跟得上；供数不足只出现在每个 1 MB 循环尾端 | **次要**（占总时长 17.7%，+22% 空间） |
| C. 接收窗口（rwnd）封顶 | ws ≥ 5 → rwnd ≥ 703 KB ≫ flight 136 KB；且单次连发 405 KB | **排除** |
| D. 协议结构 / 控制帧开销 / 文件边界空泡 | 正向流 26.6 s 内 0 个文件边界；控制帧仅 264 个 / 0.33 MB（占正向数据量 0.18%） | **排除** |
| E. **单连接 TCP 拥塞窗口受丢包与环路时延共同压制** | flight 中位 136 KB、环路 ≈ 18–20 ms、真实丢包 0.358% 且成串（队列溢出）、Mathis 量级吻合 | **✅ 根因** |
| F. 链路本身只有 ~54 Mbit/s | 100 ms 粒度峰值 20.3 MB/s、1 s 峰值 10.04 MB/s，说明主机侧可持续 ≥80 Mbit/s，但**无法据此断定链路容量** | **不影响根因**：只决定优化幅度（见 §5 P0） |

**注意 F 与根因无关**：无论链路上限是 80 Mbit/s 还是 1 Gbit/s，本传输都是被单连接 cwnd 卡在
136 KB 上、只跑出 6.8 MB/s —— 因为这 6.8 MB/s 是由 `cwnd ÷ 环路时延` 算出来的，而不是被链路顶住的
（若被链路顶住，发送端会持续灌满、不会 98.3% 时间空闲，也不会 95% 的突发都紧跟 ACK）。
F 只回答「修好之后能快到多少」：

- 若链路有余量（如千兆/5 GHz Wi-Fi），**并行连接**可近似线性提速（本次 6.8 → 20~50 MB/s 量级）；
- 若链路本身就是 ~80 Mbit/s，则并行只能把损失的 23%~33% 找回来，应改走有线/5 GHz。

**E 的机理链**（与代码无关的物理层事实，但必须理解才能选对方案）：

```
链路队列溢出（成串丢 4~62 段）
  → TCP 快速重传 + cwnd 减半（CUBIC）
  → cwnd 稳定在 100~400 KB 带
  → 吞吐 = cwnd / 有效环路时延(18~20 ms) ≈ 6.8 MB/s
  → 每个 RTT 只能推进一个窗口 → 空闲 98%
```

> 补充说明：接收端 ACK 聚合（每 ~43 KB 一个 ACK，约 30 段）拉长了「窗口推进的节拍」，
> 使有效环路时延（18 ms）远高于物理 RTT（下界 5.15 ms），进一步压低了 `cwnd/RTT`。
> 这是接收端 TCP 栈行为（GRO/延迟 ACK），**Node 应用层无法直接控制**。

## 5. 优化方案

按「先验证、再动代码；收益大、风险低优先」排序。

### P0（先做，10 分钟）——测出路径上限，决定**并行能提速多少**

> 注意：P0 不判断「为什么慢」（§1 已判定），只判断「修好之后能快到多少」，
> 以及丢包究竟来自链路还是本机。P1 是否值得做、目标定多高，由它决定。

| 动作 | 目的 |
|---|---|
| `iperf3 -c <对端> -P1 -t 20` | 单连接上限（对比本次 6.8 MB/s） |
| `iperf3 -c <对端> -P8 -t 20` | **路径是否有余量的判据**：-P8 ≫ -P1 则并行有效 |
| `ping -c 200 <对端>` | RTT / 抖动 / 丢包（判断 Wi-Fi 或中间设备） |
| 确认两端链路类型（有线/2.4G/5G）、AP 型号、是否跨 AP/跨 VLAN | 定位丢包来源 |
| 传输期间避免同主机的大流量（本次抓包里同主机有外部 HTTPS/视频小流量） | 排除竞争 |

**决策树**
- `-P8 ≥ 2× -P1` → 路径有余量 → **P1 并行传输是主方案**，目标：大文件吞吐 ≥ 0.8 × `iperf3 -P4`。
- `-P8 ≈ -P1 ≈ 10 MB/s` → 链路即天花板 → **不要改协议**，改网络（有线 / 5 GHz / 换 AP / 避开干扰）。
- `-P1` 明显高于 6.8 MB/s 且几乎无丢包 → 说明丢包来自本应用的发送突发或系统设置 → 先查 Wi-Fi 驱动队列与 `netstat -s -p tcp` 的重传计数。


### P1（主方案）大文件分段并行传输

**为什么是它**：cwnd 是**每连接**独立的资源。单连接被丢包压在 136 KB，
N 条连接就有 N × 136 KB 的总在途量，丢包恢复也互不牵连（一条减半不影响其他）。
这是在不改网络的前提下唯一能成倍提升的手段，业界（aria2/迅雷/浏览器多连接下载）已验证。

**改动范围**

1. **协议扩展（向后兼容）**
   - `HELLO` 增加能力位（如 `features: ['range-v1']`）；`OFFER` 增加 `rangeSupport`；
     `ACCEPT` 回带 `rangeSupport`。**只有双方都声明支持且文件 ≥ 阈值（建议 16 MB）才走分段**，
     否则完全沿用现有单连接路径（旧版本行为不变）。
   - `FILE_HEADER` 增加 `offset`、`length`（缺省 = 0 / size）；`FILE_DONE` 回带 `offset`。
2. **发送端**（`src/main/network/sender.ts`）
   - 对 ≥ 阈值的文件：`K = clamp(ceil(size / 16 MB), 2, 8)`，开 K 条连接（或一个连接池），
     第 k 条用 `createReadStream(absPath, { start, end, highWaterMark })` 发第 k 段
     （`pipeFile` 可直接复用，只需支持 offset 语义与 `FILE_HEADER/FILE_DONE` 带 offset）。
   - 控制帧（`RECV_PROGRESS`/`FILE_ACK`）按段回传，发送端进度改为「各段已收字节求和」（无重叠，无需去重）。
   - 其余小文件仍走单连接流式，避免连接数爆炸（建议全局并发上限 4~8，按文件大小动态分配）。
3. **接收端**（`src/main/network/receiver.ts` + `src/main/storage.ts`）
   - 关键点：**用定位写（positional write）替代顺序 WriteStream**。
     `AtomicSink` 增加 range 模式：`fs.promises.open(partPath, 'w')` 后
     `await fh.write(buf, 0, buf.length, offset + written)`；各段可乱序落盘，天然无 FIFO 约束。
   - 同一文件的多个段共享一个 `.part` 与一个 sink 注册表（key = `transferId + path`）；
     记录 `doneRanges`，**当且仅当所有 range 完成**才 `fh.close()` + `fs.rename()`（原子语义不变）。
   - 写盘错误/磁盘满语义不变（发 `ERROR` + 断开 + 清理 `.part`）。
   - 进度：各段 `written` 求和即唯一字节数（段不重叠）。
   - 内存：**水位必须按传输共享**，不能每连接 384 MB（`receiver.ts:40`）。
     建议单传输总水位降到 128 MB 高 / 32 MB 低，再按连接数分配。
4. **失败语义**：某段连接断开 → 优先仅重试该段（有界次数），失败则整文件失败并清理；
   先实现「整文件失败」也可接受，避免复杂状态机。
5. **预期收益**：路径有余量时 ≈ 线性（受链路封顶）；仅这条就能把 6.8 MB/s 推到
   路径上限（P0 测得的 `iperf3 -P4` 量级）。
6. **代价/风险**：中等。核心新增是「定位写 + 段完成合并」，其余复用现有协议与水位逻辑。
   必须新增集成测试：段乱序完成、单段失败、旧版本对端（能力位缺失）回退单连接。

### P2（配套，独立收益 +22%）发送端要「提前准备下一块」，而不是等排空

> **状态：已实现（2026-10-11）**。改动仅限 `src/main/network/sender.ts` 的 `pipeFile`：
> 新增 `READ_AHEAD_LOW_BYTES = 4 MB` / `READ_AHEAD_HIGH_BYTES = 8 MB`；暂停判据由
> 「`write()` 返回未写完」改为「积压 ≥ 高水位」；恢复信号由 `drain`（积压归零）改为
> **写入回调（该块交给内核）时检查积压 < 低水位**；顺带移除 `drain` 监听器（少一个每文件挂载的监听器）。
> 验证：`tests/unit/sender-readahead.test.ts`（假套接字，确定性）+ 
> `tests/integration/sender-readahead-socket.test.ts`（真实套接字、对端不读制造背压）。
> 实测：对端不读时发送端预读 **9 块 / 积压 7.00 MB** 才停（旧实现为 1 块 / 1 MB）；全量 73 个测试通过。
> **已知副作用（可接受）**：发送端本地 `sent` 计数（仅在旧版对端缺 `RECV_PROGRESS` 时用作进度回退显示）
> 会比实际上线数据领先最多约 8 MB；新版对端走对端回报的真实进度，不受影响。
> **尚待现场验证**：+22% 的收益需在同一真实路径上复测抓包确认（验收标准见 §6）。

**现状**（`sender.ts:52-107`、`sender.ts:226-244`）：读流 `highWaterMark = 1 MB`，
每写一块就 `if (!socket.write(buf)) stream.pause()`，而 Node socket 写水位只有 16~64 KB，
**所以每次 `write()` 都返回 false → 每个 1 MB 都要 pause**，直到 `drain`（缓冲归零）才 `resume`
→ 每次都要等一次新的**磁盘读**才继续发 → 每 1 MB 给链路留一个空洞。
抓包证据：>25 ms 的间隙中「在途 < 8 KB」的合计 **4.72 s（占总时长 17.7%）**，修掉上限 +22%。

**改法（真正的「提前准备下一笔」：低水位预读，而不是等排空）**

关键点：**恢复读盘的时机必须早于「积压归零」**。若像先前草稿那样只在 `drain`（积压=0）时恢复，
空洞只是从「每 1 MB 一次」变成「每 4 MB 一次」，并没有被消除 —— 因为恢复的那一刻应用手上仍然是空的。
正确做法是维持一段**预读积压**：积压高于上限才暂停，降到下限就立刻恢复，使读盘始终发生在
「内核里还有存量」的时候，从而与发送完全重叠。

```ts
const READ_HIGH = 4 * 1024 * 1024   // 预读上限（内存约束）
const READ_LOW  = 1 * 1024 * 1024   // 预读下限：降到它就马上补下一块
onData: socket.write(buf, () => {                      // 写入回调 = 该块已交给内核的时点
          if (socket.writableLength < READ_LOW) stream.resume() })
        if (socket.writableLength >= READ_HIGH) stream.pause()
```

不用 `drain` 作为恢复信号（它只在归零时触发，本身就太晚）；改用写入回调配合
`socket.writableLength`（其含义正是「已写入但尚未交给内核的字节数」）。

**预读水位该开多大（可验证的设计判据）**

链路不断流等价于「预读耗尽之前，下一块必须到位」：

```
内核发送缓冲 B + 应用预读积压 ≥ 读一块所需时间 × 链路速率
```

- 千兆链路（125 MB/s）+ 读一块 20 ms → 预读需 ≥ **2.5 MB**（内核缓冲通常只有 128~256 KB，杯水车薪）；
- 百兆链路（12.5 MB/s）+ 读一块 20 ms → 预读需 ≥ **250 KB**；
- 慢盘/网络盘（读一块 50 ms）+ 千兆 → 预读需 ≥ **6.25 MB**。

这条式子同时说明：**水位不是随手填的常数，而要按「最坏读盘延迟 × 链路速率」定**；
链路越快、盘越慢，就越需要深的预读（代价是内存，所以上限仍要封顶）。

**为什么现在的写法会浪费链路时间（机理，必须说清才有说服力）**：现在的管道深度只有 1 个 chunk。
`drain` 触发的那一刻，数据已全部在内核发送缓冲里，App 手上**一个字节都没有**，必须**再去读一次盘**，
等这次读回来才能继续写。若「内核发送缓冲排空所需时间」小于「这次读盘 + 事件循环的延迟」，
链路就出现一段无人供数的空洞；每 1 MB 重演一次（本次 181.83 MB ≈ 182 次循环）。
注意空洞出现在 **drain 之后、下一个 chunk 到位之前**，既不是「等磁盘写」（发送端不写盘），
也不是「等 drain 本身」（等 drain 期间内核仍在持续发送）。

效果：pause/resume 周期从「每 1 MB」变成「每 ~4 MB」，本地读盘/调度延迟被积压吸收，
链路不再因喂数空洞而空闲。**验收：§3.7 中「供数不足」时长占比 < 5%，同路径吞吐 ≥ 8.3 MB/s。**

**为什么「改数据块大小」不是正解（顺带纠正两个直觉）**

设读盘速率为 r、链路速率为 R、内核发送缓冲为 B、数据块为 C，则

```
总空闲 ≈ 读盘总耗时 − 循环次数 × 内核缓冲可覆盖的时间
       = S/r − (S/C)·(B/R)          （前提：C/r > B/R，否则该项为 0）
```

- **「不是块设得过小」**：只要块大于套接字水位（16~64 KB），`write()` 就必然返回未写完并触发暂停，
  所以 512 KB、4 MB 与 1 MB 是**同一个结构性问题**，与数值大小无关 —— 病根在「暂停时机」。
- **「把块调大反而更慢」——正确**：块越大 → 循环次数 `S/C` 越少 → 被摊掉的固定覆盖量 `B/R` 越少
  → **总空闲越多**。抓包上会看到「停顿次数变少、单次停顿变长、总空闲时间变多」，
  这正是该问题最容易被直觉带偏的地方。
- **「把块调小只能减轻症状」**：块小到「读一块的时间 ≤ 内核覆盖时间」时空闲确实归零，
  但那是靠「读盘恰好来得及」碰巧实现，不是靠「读盘与发送重叠」。且块越小系统调用越多。
- **正解**：按积压量决定暂停时机（上文改法），让读盘与发送真正重叠；此时**块大小不再重要**
  （1 MB 可以保留，甚至可以调大以摊薄系统调用开销）。

> 注意「介质空闲」的口径：98.3% 是**抓包点（发送端递交点）**的空闲比例，
> 即「98.3% 的时间没有数据可交给驱动」。换算到链路：182 MB 若走千兆只需约 1.5 s，
> 即链路约 94% 的时间是空的。链路实际速率未知（§5 P0），故不宜直接把 98.3% 说成链路空闲率。


### P3（网络层，若 P0 显示链路即天花板或丢包来自链路）

- 优先有线；Wi-Fi 用 5 GHz 且靠近 AP；避免 2.4 GHz 拥塞信道与跨 AP 漫游。
- **若任一端是 Linux，切换拥塞控制为 BBR**（`net.ipv4.tcp_congestion_control=bbr`）：
  BBR 不以丢包为唯一信号，在 0.36% 丢包 + 高时延路径上通常有数倍提升。
  macOS/Windows 端没有等价开关（Windows 11 22H2+ 默认 CUBIC）。
- 不要为了省事去动「禁用 GRO / 关掉窗口扩大」——那会**降低**吞吐。
- 观察手段：传输前后采样 `netstat -s -p tcp`（macOS）/ `netstat -s`（Linux）的
  retransmit 计数，用差值判断丢包是本机还是链路。

### P4（独立缺陷，与本次慢无关但必须修）控制帧解析 O(n²)

`protocol.ts:185-197`（`FrameParser.push`）与 `receiver.ts:200-206`（`ctrlBuf`）
都是每收到一个 chunk 就 `Buffer.concat([累积, chunk])`，而 `MAX_FRAME_LENGTH = 64 MB`
（`protocol.ts:4`）。按 64 KB 分片收到 64 MB 的 `OFFER`（海量文件清单）时，
拷贝量约 `P²/(2·chunk)` ≈ **34 GB memcpy**，会在接收端事件循环里造成**数秒级卡顿**
（表现为「传输开始前长时间无响应」）。改法：用 chunk 列表累积，只在需要时拼接一次。

### P5（可观测性 + 内存，低成本）

- 每次传输结束打印：字节数、耗时、MB/s、pause 次数、队列峰值、ACK/重传代理指标
  （`netstat` 差值），并在 dev 模式的传输列表展示。**没有这个，下次还会靠抓包猜。**
- `receiver.ts:40-41` 的 384 MB / 128 MB 水位在本场景永不触发，却把最坏内存顶到 512 MB；
  与 P1 的「按传输共享水位」一起调小（如 128 MB / 32 MB），滞回区间保持 4:1。

### P6（流程）把「路径条件」纳入回归基线

现有 `scripts/probe-gap.mts`、`scripts/bench-transfer.mts` 跑的是**回环**。
回环不会触发写背压、也不会丢包，**因此永远复现不出本次问题**（回环 815 MB/s）。
建议增加一个「真实双机 + 可选丢包注入（如 `dnctl`/`pfctl` 或 Linux `tc netem delay 20ms loss 0.4%`）」
的压测脚本，把「丢包 + 高时延」变成可回归的验收环境。

## 7. 对既有设计文档结论的修正

`docs/receive-pipeline-design-2026-08-29.md` §1.1 的判断是：

> 「磁盘毫秒级停顿 → WriteStream 缓冲满 → socket.pause() → 零窗口 → 发送方减速 → 恢复需重爬」，
> 并以「回环 815 MB/s、无空泡」作为「协议结构没问题、问题在背压灵敏度」的佐证。

本次抓包（真实链路、单文件 ≥356 MB）给出的结论不同：

1. **零窗口通告 0 次**，接收端从未把背压传导给发送方；高水位 384 MB 在 356.7 MB 的传输里
   数学上不可能触发。→ 该机理链在本次场景**没有发生**。
2. **回环压测本身不能证伪该机理**，也不能证伪别的机理：回环不产生写背压、不丢包、RTT≈0，
   恰好把「窗口 ÷ 时延 + 丢包」这一真实瓶颈的因子全部屏蔽了，所以回环上永远看到满速。
   §1.1 的推论属于**用无法触发的实验环境给真实瓶颈归因**。
3. 接收管线解耦（方案 2）本身仍然有价值（慢盘、抖动盘、海量小文件场景），
   但**它不是本次慢的原因，也不该作为「大文件慢」的主攻方向**。
   大文件的杠杆在「多连接并行 + 发送端持续喂数」，即 §5 P1/P2。
